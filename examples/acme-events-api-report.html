16. Proposed Improvements

ImprovementPriorityReasoning
Add Idempotency-Key header to POST /bookings High Blocks mobile shipment for automated booking flows. Client generates a UUID per booking attempt; server deduplicates on key. Prevents duplicate bookings on retry.
Add delta sync support — updated_since param to GET /events and GET /events/{id}/staff High Required for offline. ISO 8601 timestamp param filters events/staff modified after a given time. updated_at is already in the Event schema — just expose it as a filter.
Add tombstones — deleted_at field to Event, StaffMember, and Booking schemas High Required for offline correctness. Without tombstones, cached data never ages out. Soft-delete pattern: mark records as deleted but return them in delta sync responses.
Add WebSocket or SSE endpoint for schedule change notifications High Required for auto-update. Minimum viable: SSE stream for event schedule changes and staff assignment updates. Reduces polling load and enables immediate update on mobile.
Add Cache-Control and ETag response headers High Enables client-side and CDN caching. Minimum: Cache-Control: max-age=60 on GET /events, ETag on GET /events/{id}. Significantly reduces repeat-request latency on mobile.
Remove or scope sensitive fields (billing_code, internal_notes, account_manager_*, hourly_rate) High PII and financial data must not be returned to field-worker mobile clients. Either define OAuth2 scopes (e.g. events:admin) or create a mobile-specific response projection that omits these fields.
Add pagination to GET /events/{id}/staff High Unbounded array is a reliability risk. Add limit (default 20, max 100) and a cursor param. Prevents large staff events from causing oversized mobile payloads.
Standardise error schema across all endpoints Med Replace all inline error schemas with $ref: Error. Add request_id to the Error schema to enable client-server log correlation. Apply consistently to 401, 404, 409, and 5xx responses.
Define and document rate limits with X-RateLimit-* headers and 429 response Med Add rate limit response headers to all endpoints and define a 429 response with Retry-After. Publish limits in spec via x-rateLimit extension. Prevents mobile apps from hammering the API on failure.
Document token refresh flow Med Add a token refresh endpoint or migrate to OAuth2 with a defined refresh_token flow. Document token expiry time and 401 sub-codes so mobile apps can distinguish expired vs invalid tokens.
Define OAuth2 scopes for least-privilege access Med Migrate bearerAuth to OAuth2. Define minimal scopes: e.g. events:read, staff:read, bookings:write. Restrict admin fields to events:admin scope.
Add locale support — Accept-Language header or locale param Med For multi-locale deployment: accept Accept-Language header and return locale-appropriate content where applicable. Add currency_code field alongside hourly_rate in StaffMember.
Migrate pagination to cursor-based on GET /events Med Replace offset/limit with cursor/limit. Return an opaque next_cursor in the response. Eliminates page-drift on live data and enables efficient delta sync when combined with updated_since.
Add deprecation/sunset policy and Sunset response header Low Define a minimum notice period (e.g. 12 months) for breaking changes. Add Sunset response header to endpoints approaching end-of-life. Add externalDocs link to changelog.
Add X-Request-Id to all responses and define SLA Low Add X-Request-Id response header (or request_id in error body) to enable mobile-server log correlation. Document latency SLOs in spec externalDocs.

VerdictNot mobile-ready
Top 3 risks:
1
Data integrity collapse under offline + retry conditions. The combination of no idempotency on POST /bookings (used in automated flows), no offline sync mechanism, and no tombstones means duplicate bookings and stale cached data are both near-certain in normal field usage. These are not edge cases — they are the primary usage scenario.
2
Sensitive data exposure to all authenticated mobile clients. billing_code, internal_notes, account_manager_email/phone, and staff hourly_rate are returned to every authenticated caller with no scope restrictions. This is a compliance and data-protection risk in a multi-locale, field-worker deployment.
3
No real-time update mechanism where auto-update is required. User confirmed schedule changes must propagate automatically to the mobile app. No WebSocket, SSE, or push endpoint exists. Polling is the only option — battery-intensive, latency-prone, and incompatible with the offline requirement.
Engineering recommendationDetail
Do not ship to mobile consumers in current state. The API lacks the foundational building blocks required for reliable mobile operation: no idempotency, no caching contract, no sync mechanism, no RTM, and sensitive data exposed without scoping. These are not optimisation gaps — they are correctness and safety gaps.
Conditions for re-evaluation Minimum gate to re-evaluate (all must be addressed):
• Idempotency-Key added to POST /bookings
• updated_since filter added to GET /events and GET /events/{id}/staff
• Tombstone field (deleted_at) added to Event and StaffMember
• Sensitive fields removed from mobile response or gated behind a scope
• Pagination added to GET /events/{id}/staff
• Cache-Control headers added to GET endpoints
